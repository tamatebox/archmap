# archmap

archmap maps a repository into components (packages, modules, files, external dependencies) and the dependencies observed in manifests and imports, each with `file:line` evidence. It answers structural questions (where code lives, what imports what, what a change may reach): open the `file:line` it gives, and search normally for what it does not map, such as error messages, configuration values, dynamic loading and relations beyond imports. The code decides what is true; archmap decides where to look.

Its MCP tools (`summary`, `query`, `impact`, `check`) say what they take; a client that loads tools on demand may list them by name only until you search its tools for `archmap`. Without them, the `archmap` CLI has the same commands: `archmap summary .`, `archmap query <target>`, `archmap impact <target>` and `archmap check`, with `--path <root>` for another root (`summary <root>`) and `--format json` for every piece of evidence. If neither the tools nor the command exist, archmap is not installed: tell the user (`cargo install --git https://github.com/tamatebox/archmap archmap-cli`, again after the plugin updates) and continue without it. Do not read `.archmap/graph.json`: it is an export that `archmap scan` writes into the repository.

## Reading the output

- **Observed, not inferred.** Names are package, directory and module names, not responsibilities; label any role you infer as inference.
- **A missing edge is not a missing dependency.** `## Coverage` and `Not mapped` show what the map misses, and runtime coupling (HTTP, databases, queues, subprocesses) is unseen. `components: 0 shown` means archmap cannot read these languages; continue without it. `Imported by: none` (or `none resolved`) does not mean unused; search the code before calling anything unused. In TS/JS, `unresolved` is a path or alias that matches no file, and framework entry files (`page.tsx`, `route.ts`, configs) and scripts started from a command or a config string have no importers by design, nor do the globals of a `script` (a file without imports or exports, counted in Coverage).
- **Everything is rolled up to one depth.** Every tool and command defaults to the same depth; if you set `depth`, keep that value across calls, since results at other depths name other components. Deeper modules fold into their ancestor (`folded: N`), and on a folded name `query` and `impact` answer for the ancestor (`folded from`); a name of one file (a TS/JS file, a Rust module without submodules) still gets the file's `Imported by`. `imports: N` counts statements in production code and `tests: M` those in test code, which `check` rules and cycles leave out; `declared: yes` means a manifest declares the dependency too. A capped list says so: in summary an `omitted:` line names the query for the rest; in query and impact the heading reads `N, showing M`, and the answer ends by saying how to see every entry.
- **Locations say how a statement runs.** `(local)`: inside a function, so it runs when the function is called; `(type)`: types only, which never run; `(test)`: test code; `(export)`: a re-export, which passes names on; `(mock)`: a test's mock that replaces the module for the test's whole run; `(via <file:line>)`: reached through a re-export. A location is where an import is written, not where the name is used, and uses inside the defining file are no imports. A file's `Imported by` lists the statements that load it; a symbol's lists those that take its name, and `May use` those that take its whole module. In `impact`, `Direct dependents` come with their statements into the target, most first, and `Transitive dependents` nearest first, with their steps and the file the walk reached them from (open that file to see why), or the component their manifest declares, with the line that declares it; a component that holds the target names the files of it reached (`ts-shop (src/index.ts)`), not all of it; `Imported by` also lists statements inside the target's own component, which `Direct dependents` never names, and `Tests to run again` names the test files to run again with how each reaches the target (`takes it`, `takes its module whole`, `runs first: <entry>`, `through <file>`; a test that takes it runs it, one through other files may not), ending with those left out because their mocks replace a module on the way.
- **`Used at` is where a Rust, TS or JS symbol is used**, in `query`: each place marked `(call)`, `(new)`, `(jsx)`, `(type)` or `(read)` (passed as a value), `as <name>` when the code names it otherwise, never a match in a comment or a string; `never used` lists imports whose binding nothing uses, `never named` imports of the whole module that never name it, and `mocked` the keys of tests' mock factories that stand in for a TS/JS symbol, no use but places to edit with it. A method that is not static (in Rust, one taking `self`) lists only the uses through its class or type and `this` or `self`. `Not traced` names what may still reach it: a module used as a value (`whole module`), statements not read again (`uses`), calls through a value of the type (`values`, with the imports of the class that may make them), and through a subclass (`subclasses`). Python symbols have no `Used at`: search for their callers.
- **Names are how imports write them.** A Rust module is named as `use` writes it (`archmap_core::graph`), and a module of a binary under `src/bin/`, a test, an example, a bench or the build script by its path in the package (`tests/common/mod.rs`); a TS/JS file by its path from `src/` with its extension, so `lib/money.ts` is `src/lib/money.ts` on disk; a Python module by its dotted path. An import name is the name the code imports (`torch`), not the distribution's. An import of a stylesheet, image or JSON file shows under the importer's own component, or under the package that holds the file.
- **Check what a name resolved to.** Names repeat: read the `id:` line (in impact's JSON, `target`, or `module` for an import name), and retry with the id or a file inside it when a result is surprising. Where a name repeats, summary lists show the id instead. A target that names several things lists them as candidates (exit 1 from the CLI); retry with one of their ids or with `./<path>`.
- **impact is reachability, not a verdict.** Python and Rust are traced file by file, a Python package's `__init__.py` reached from the imports of a module below it that come from outside the package (listed as `Imports below`), and TS/JS through tsconfig paths, `require`, `import()` and test mocks; in every language an import through re-exports counts for the file that defines the name. What could reach a target unseen ends the answer as `Not traced` (`not_traced` in JSON): calls that load modules by computed names, imports named like the target that resolved to no file, Rust macro calls whose arguments were not read and that name the target, files the analyzer did not read, a script's globals, a file nothing imports; search for those before calling anything unused. Not listed anywhere: a Rust crate's own unit tests, so search for callers before changing a Rust signature. In repositories with Python packages, read `Direct dependents` in `impact` first: `Transitive dependents` widen through an `__init__.py` that may use what it imports, while a barrel (a TS/JS re-export, an `__init__.py` that only passes names on) leads on only to what may take the changed names, and `Not traced` names it as `barrels`, since a rename or an error on load breaks whatever else loads it. Listed components may not use what you change; unlisted ones may still depend on it.
- **Changed in the same commits is history, not dependency.** `impact` lists the files committed together with the target in the root's git history, those that change mostly with it first: `2 of the target's 4, 2 of its own 10` says how many commits they share out of each, so a file in most commits (a lockfile, a changelog) is a hub, not a partner. It shows coupling no import shows (configuration, test data, other languages). The `history:` line says what was read; a shallow clone or a bounded read hides older commits (`Not traced` says so), and uncommitted changes never count.
- **`'#123'` is work, as GitHub records it.** `query '#123'` (quoted in a shell) reads the snapshot under `.archmap/`: the item's links by type (`Closes`, `Closed by`, `Cross-referenced by`, ...) and a pull request's commits matched to the local history by SHA. A commit without a match is no proof the work was not merged (squash and rebase merges rewrite SHAs); `Not traced` names the links an item's end cannot see, and the snapshot line says its range. Without a snapshot the answer says where it looked; `archmap fetch github` writes one through the network and the user's gh login, so leave fetching to the user.
- **check reports, signals observe.** `check` findings carry evidence; its cycles count only imports that run, so `(local)` ones close cycles and `(type)` ones do not. `signal:` lines are observations, never failures.
- **Components cover everything under the root**, fixtures and vendored code included: check the path before treating one as product code.
